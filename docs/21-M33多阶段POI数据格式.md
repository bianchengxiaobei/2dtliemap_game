# M33 多阶段 POI 数据格式（F5-T1/T2/T3/T4/T5/T6/T7）

> 状态：**M33-F5-T1/T2/T3/T4/T5/T6/T7 已完成（2026-11-16）**。适用 `pois-v1` 的可选扩展；数据契约由 T1 完成，世界级阶段运行时/存档与只读网络镜像由 T2 完成，门禁/钥匙物品/供电/可选入口与路线由 T3 完成，阶段精英/Boss、机制、脱战重试与奖励一次由 T4 完成，结构化 HUD、叙事、完成/失败面板与世界地图阶段标记由 T5 完成，默认 M31 的诊所/检查站/农场仓内容包由 T6 完成，双客户端共享阶段/个人奖励/重启恢复与 15.3 游戏分钟跨包循环由 T7 完成。实现位于 `src/game/Poi.{h,cpp}`、`PoiComponents.h`、`PoiStageCombat.h`、`WorldMap.{h,cpp}`、`src/ui/WorldMapPanel.cpp` 与两套 HUD，契约/运行时测试为 `tests/test_poi.cpp`、`tests/test_world_map.cpp`、`tests/test_ui.cpp`、`tests/test_content_hash.cpp`、`tests/test_entity_save.cpp`、`tests/test_zombie_variants.cpp`、`tests/test_m33_f5_t7.cpp`、`test_network_world_persistence.cpp` 与 `tools/tests/test_f5_poi_content.py`。

## 1. 兼容原则

- `config/game.json` 的 `pois.defs[]` 和 mod 的 `content/pois.json` 仍使用 `format: "pois-v1"`。
- 新增字段全部可选。没有 `stages` 的 POI 继续走原有单段 `task`，容器、守军、任务奖励、HUD 与存档行为不变。
- 有有效 `stages` 时，`task` 可以省略；也可以用 `task` 保留单段摘要。没有 `task` 且没有有效阶段时，该 POI 跳过。
- 阶段数组顺序就是阶段顺序；`next` 只能指向数组后面的阶段，禁止回边/环。
- 非法阶段或非法引用按单条跳过；依赖被跳过阶段的后续阶段、入口、分支、Boss、叙事也会被跳过/禁用。合法条目保留。
- 内容指纹升 **v21**，新字段、数组顺序和数值全部参与指纹；联机双方仍必须在握手阶段一致。
- mod 只能在基础定义后追加新 POI，不能覆盖同 id 定义；staged POI 与旧 POI 使用同一套合并规则。

## 2. `stages[]`

最多 8 个阶段。阶段 id 使用小写字母、数字、`_`、`.`，最长 64 字节，同一 POI 内唯一。

```json
{
  "id": "find_key",
  "kind": "loot",
  "hint": "在药房找到门禁卡",
  "target": "poi_hospital_pharmacy",
  "x": 41.5,
  "y": 85.5,
  "radius": 2.0,
  "count": 1,
  "next": [ "open_gate" ],
  "requires": [ "front_key" ],
  "reward": { "xp": 20.0, "item": "bandage", "count": 2 }
}
```

| 字段 | 类型 | 必填 | 默认/范围 | 说明 |
|---|---|---|---|---|
| `id` | string | 是 | 1–64 字节 | 阶段唯一 id |
| `kind` | string | 是 | `reach/interact/kill/loot/power/choice` | 阶段类型 |
| `hint` | string | 否 | 1–256 字节 | 阶段提示；运行时缺失时可用类型默认文案 |
| `target` | string | 视类型 | 1–64 字节 | `interact/loot/power` 必填；`reach/kill/choice` 可选 |
| `x`,`y` | number | 视类型 | -1000000–1000000 | `reach` 必填；其他类型可省略，缺省为 POI `markerX/markerY`；必须成对出现 |
| `radius` | number | 否 | 0.5–64，默认 1.5 | 到达/交互判定半径 |
| `count` | int | 否 | 1–9999，默认 1 | 击杀/搜刮目标数量，具体由 T2 解释 |
| `next` | string[] | 否 | 非 `choice` 最多 1 个；`choice` 2–4 个 | 后续阶段 id，只能指向后面的阶段 |
| `requires` | string[] | 否 | 最多 4 个 | 需要的 `keys[].id`；钥匙来源阶段必须在该阶段之前 |
| `reward` | object | 否 | 见下 | 阶段一次性奖励 |

### 2.1 阶段类型

| `kind` | 目标 | 说明 |
|---|---|---|
| `reach` | 坐标/半径 | 到达指定地点 |
| `interact` | `target` | 与门禁、开关、尸体、文件等交互 |
| `kill` | 可选 `target` + `count` | 清理普通/精英/Boss 目标 |
| `loot` | `target` + `count` | 取得钥匙、文件、样本等 |
| `power` | `target` | 启动发电机/恢复供电 |
| `choice` | `next` | 选择路线；必须有 2–4 个后继阶段 |

### 2.2 阶段奖励

```json
"reward": { "xp": 20.0, "item": "bandage", "count": 2 }
```

- `xp`：0–100000，默认 0。
- `item`：可选物品 id；出现时 `count` 为 1–9999，默认 1。
- 只写 `count` 不写 `item` 视为非法阶段。
- 奖励只由阶段完成时结算；T1 不生成/发放奖励。

## 3. `entries[]`

最多 8 个入口/路线起点，用于 T3 的可选入口。

```json
{ "id": "back_entrance", "label": "后门", "x": 43.5, "y": 53.5,
  "stage": "morgue", "requires": "back_key" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 入口唯一 id，规则同阶段 id |
| `label` | 否 | 显示名，1–64 字节 |
| `x`,`y` | 是 | 入口坐标 |
| `stage` | 否 | 进入后从该阶段开始；必须引用有效阶段 |
| `requires` | 否 | 需要的 `keys[].id`；必须引用有效钥匙 |

## 4. `keys[]`

最多 8 个钥匙/门禁物品。`requires` 引用的是这里的 `id`，不是物品 id。

```json
{ "id": "front_key", "item": "keycard_front", "name": "前门钥匙卡",
  "source": "find_key", "consumed": true }
```

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `id` | 是 | — | 钥匙唯一 id |
| `item` | 是 | — | 实际物品 id，由 Python/内容测试校验存在性 |
| `name` | 否 | 空 | 显示名 |
| `source` | 否 | 空 | 发放该钥匙的阶段 id；空表示外部来源/任意来源 |
| `consumed` | 否 | `true` | 使用后是否消耗；T3 实现 |

阶段引用钥匙时，如果 `source` 有值，来源阶段必须位于该阶段之前；否则该阶段跳过。这样可以阻止“先要求钥匙、后发放钥匙”的死锁配置。

## 5. `branches[]`

最多 2 条可选路线。

```json
{ "id": "morgue_route", "name": "太平间路线",
  "from": "choose_route", "stages": [ "morgue", "boss" ] }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 分支唯一 id |
| `name` | 否 | 显示名，默认等于 id |
| `from` | 否 | 分支起点阶段 id；必须存在 |
| `stages` | 是 | 1–8 个阶段 id，必须存在且不重复 |

分支只描述阶段集合，不复制阶段定义；同一阶段可以出现在多条路线中。T1 不要求路线互斥，也不自动完成未选路线。

## 6. `boss`

可选对象；字段非法或引用缺失时只禁用 Boss，不丢弃整个 POI。

```json
{ "name": "院长", "variant": "armored", "stage": "boss",
  "mechanic": "summon", "count": 1 }
```

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `name` | 是 | — | Boss 名称 |
| `variant` | 是 | — | 复用敌人变体/精英 id |
| `stage` | 否 | 最后一阶段 | 绑定阶段 id |
| `mechanic` | 否 | 空 | `summon/charge/fortify`；空表示无特殊机制 |
| `count` | 否 | 1 | 1–8 |

T4 起 Boss 只在实际绑定的 `kill` 阶段生成；`count` 会截断到阶段 `count`，剩余目标由 `stage.target` 选择精英变体（未知值回退 `armored`）。`summon` 增援计入 `Summon` 角色但不计入阶段击杀；`charge` 为周期性速度冲锋；`fortify` 复用 `ZombieSpecial::Breaker` 破坏玩家工事。Boss 默认生命倍率/脱战/召唤/冲锋参数由 `config/game.json` 的 `pois.boss.*` 控制，详见 §12。

## 7. `narrative[]`

最多 16 条叙事/文件，可绑定阶段或作为搜刮物。

```json
{ "id": "note_intro", "stage": "approach",
  "text": "医院封锁记录", "item": "hospital_note" }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 叙事唯一 id |
| `stage` | 否 | 绑定阶段；必须存在 |
| `text` | 是 | 1–512 字节正文 |
| `item` | 否 | 可作为搜索物的物品 id |

## 8. 校验与跳过规则

1. `pois`/`defs` 结构错误会使整份基础配置或 mod 文件失败；mod 文件失败时保留旧候选。
2. 单条 POI、阶段、钥匙、入口、分支、Boss、叙事非法时逐条跳过并告警；合法条目保留。
3. 阶段 `id` 重复、未知 `kind`、`reach` 缺坐标、`interact/loot/power` 缺 `target`、`choice` 后继不足 2 个、非 `choice` 超过 1 个后继、奖励字段越界都会跳过该阶段。
4. `next` 指向不存在或前面的阶段、`requires` 引用不存在/未来来源的钥匙时，该阶段跳过；依赖它的后续阶段继续按引用规则级联跳过。
5. 没有有效阶段且没有合法 `task` 的 POI 跳过。
6. 旧 `pois-v1` 没有新字段时，所有新数组为空、Boss 禁用、`task` 必填，行为与 F5 前一致。
7. mod 追加重叠 id 跳过；staged POI 不生成地图房间/墙体，坐标和可达性由作者保证。
8. T2 仍复用旧 POI 容器校验：`containers` 必须是数组，且至少要有一个合法容器条目；纯阶段 POI 暂时也要放一个容器占位。

## 10. T2 运行时与存档

- 世界状态：`ecs::PoiWorldProgress` 保存 `PoiProgress[]`，位于高段 StableId `0xF333504F49575001`，作为内置存档组件 `PWPR` 随实体快照保存；`PoiProgress` 记录当前/失败阶段、完成阶段、已选分支、已获得钥匙、供电、失败/重试、当前击杀进度和守军基线。
- 启动：单机/服务器在任一玩家进入 POI marker 16 格内时启动第一阶段；世界进度所有玩家共享，客户端不自行推进。
- 权威条件：`reach` 按当前玩家位置/半径；`kill` 按阶段敌人存活数下降累计到 `count`（T4 起只统计 `PoiStageEnemy` 的 Boss/Elite，普通 POI 守军不计入）；`loot` 按玩家背包/装备中 `target` 物品数达到 `count`；`interact`/`power` 走 `SignalPoiStage`，`power` 同时写入 `powered`；`choice` 走 `ChoosePoiBranch` 并写入 `chosenBranch`。T3 已接真实门禁/钥匙物品消耗/发电机与路线选择，T4 已接阶段刷怪/Boss 失败钩子。
- 阶段完成：完成阶段只记录一次，发放 `source == stage.id` 的钥匙标记，返回一次 `PoiStageUpdate`；`next` 自动进入下一阶段，`choice` 暂停等待分支。阶段奖励由玩家级 `PoiTasks.rewardClaims` 的 `poiId.stageId` 幂等键结算，旧 `PoiTasks` 存档 v1 仍可读，新档写 v2；服务器仅向阶段完成时 POI 32 格内的玩家发奖。
- 失败/重试：`FailPoiProgress` 记录失败阶段但保留已完成阶段；`RetryPoiProgress` 清失败、重开失败阶段并递增尝试次数。T4 起 Boss 在 `pois.boss.resetRange` 外持续 `resetSeconds` 会失败并清除阶段敌人；服务器团灭同样失败。玩家回到 POI marker 16 格/入口 6 格内自动重试并重新生成阶段敌人。
- 网络：`PlayerState v22` 在尾部追加 `poiStageProgress[]`（id、阶段序号/总数/完成数、`awaitingChoice/failed/powered` flags、当前阶段 id、已选分支），旧 v21 负载缺省为空；客户端只读。
- 重启：已完成 staged POI 不再补生成守军；容器仍按地图生成/读档恢复。服务器集成用例验证三阶段推进、世界进度落盘、重启后完成阶段与客户端镜像恢复。
- 限制：T2 不生成阶段专属敌人/Boss、不消费钥匙物品、不执行门禁/发电机/路线 UI、不显示阶段 HUD/地图阶段标记；这些由 T3–T5 完成。

## 11. T3 门禁、钥匙、供电与可选路线

- 纯函数：`FindPoiStage`/`FindPoiKey`/`FindPoiEntry`、`StartPoiProgressAtStage`、`MarkPoiKeyAcquired`、`PoiStageKeyAwards`、`PoiAvailableBranches`、`PoiKeyDisplayName`、`PoiStageObjectiveText`、`PoiStageRequiredKeysText`、`PoiChoiceText`。
- 钥匙发放：阶段完成时，`keys[].source == stage.id` 的钥匙物品发给单机玩家，或服务器阶段完成时 POI 32 格内玩家；世界进度同时写入 `acquiredKeys`。钥匙物品未注册时不发物品但仍保留世界钥匙标记，避免内容错误造成无提示卡死。
- 钥匙消耗：`interact/power/choice` 交互前检查 `requires` 对应物品；`consumed=true` 消耗 1 件，`false` 保留。钥匙必须在玩家背包中；缺失时显示“缺少钥匙：<名称>”。
- 门禁：`interact` 阶段在阶段坐标/半径内按 `E` 执行；当前实现是逻辑门禁，不绑定可开关的建造成门实体。
- 供电：`power` 阶段检查钥匙后，按 `homestead.power.enabled` 消耗 `homestead.power.fuelItem`（默认 `fuel_can`），启动阶段坐标附近已有的 `ecs::Generator` 并写入 `PoiProgress.powered`。电力系统关闭时允许手动合闸；无燃料显示明确提示。
- 入口：角色靠近 marker 或满足钥匙条件的 `entries[]` 坐标时开始；入口可按 `entry.stage` 从非首阶段开始，并按键的 `consumed` 消耗入口钥匙。当前入口为靠近自动进入，没有独立入口选择面板。
- 路线：`choice` 阶段显示 1/2 路线提示，快捷栏 1/2 调用 `ChoosePoiBranch`；服务器通过 `PoiInteract=60`（`payload.index` = POI 定义索引，`payload.targetIndex` = 可用分支索引）复核距离、阶段、钥匙和路线。
- 提示：单机/服务器 HUD 的 POI 指引显示阶段序号、目标、钥匙/供电和路线；交互 action hint 显示 `按 E`、缺钥匙或缺燃料。完整任务/地图 HUD 与 1280 截图留 T5。
- 测试：`M33-F5-T3*` **2/2（66 assertions）**，覆盖钥匙物品/入口/路线纯数据、缺钥匙/有钥匙、燃料、实际 `ecs::Generator` 启动、服务器路线选择与入口；Debug **1046/1046（141952 assertions）**、Release **1046/1046（141966 assertions）**、Python **114/114**。启动烟测 `build/m33_f5_t3_startup_final/startup_nomods.out.log`：POI 4 个、内容指纹 `0x38f10fa308f0fc42`、tick=600、stderr 0。
- 限制：T3 不新增内置 staged 内容（T6）；不做多层建筑/真实门实体/完整发电机电网；入口无独立 UI；Boss/阶段战斗留 T4，完整阶段 HUD/地图/叙事与 1280 截图留 T5。

## 12. T4 精英/Boss 与阶段战斗

- 纯函数：`BuildPoiStageEnemyPlan`/`PoiStageHasBoss`/`PoiBossStage`/`PoiBossMechanicFor`/`PoiBossMechanicName`/`PoiBossMechanicText`；`PoiStageObjectiveText` 对 Boss 阶段显示名称、机制和击杀进度。
- 阶段敌人：`kill` 阶段生成 `stage.count` 个 `PoiStageEnemy`；Boss 阶段先用 `boss.count` 生成 Boss（截断到 `count`），剩余由 `stage.target` 选择精英变体。实体同时带 `PoiGuard` 与 `PoiStageEnemy`，角色为 `Boss/Elite/Summon`；`Summon` 不计入 kill 目标。
- Boss 机制：`summon` 每 `summonIntervalSeconds` 在 Boss 附近生成 `summonCount` 个快速召唤物，受 `summonMax` 存活和 `summonTotal` 总上限；`charge` 每 `chargeIntervalSeconds` 在 14 格内触发 `chargeSeconds` 的速度倍率冲锋；`fortify` 给 Boss 附加 `ZombieSpecial::Breaker`，优先破坏玩家工事。Boss 生命乘 `healthScale`。
- 失败/重试：Boss 存活时若没有玩家在 `resetRange` 内持续 `resetSeconds`，单机/服务器将当前阶段标记失败并清除阶段敌人；服务器在玩家死亡且无存活队友在范围内时立即失败。失败后玩家进入 marker 16 格或入口 6 格内会自动 `RetryPoiProgress`、重新生成敌人。已完成阶段和 `rewardClaims` 保留，奖励不重复。
- 存档/网络：`PoiStageEnemy` 注册 `PSEN` 内置存档组件（组件数 51），服务器重启后已有阶段敌人不重复生成；`PoiBossRuntime` 是运行时计时器，不存档，读档后按机制重建。`PlayerState v22` 与内容指纹 v21 不变。
