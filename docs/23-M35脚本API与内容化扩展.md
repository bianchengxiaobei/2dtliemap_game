## 1. 背景：现在为什么还要改 C++

### 1.1 已经脚本化 / 数据化的部分

| 层 | 现状 | 关键实现 |
|---|---|---|
| 数据内容 | items / recipes / buildings / loot / forage / pois / missions / settlements / world_events / companions / vehicle_mods / crops / animals / fire 均可用 `content/*.json` 追加；单机可事务热重载 | `src/game/ModContent.cpp`、`docs/modding.md` §3.6 |
| 行为脚本 | Lua/Python 双后端；`mod.json` 选择后端；脚本热重载约 1 秒 | `src/script/ModLoader.cpp`、`src/script/ScriptManager.cpp`、`src/script/LuaRuntime.cpp` |
| 事件 | 事件表 v1：`OnTick/OnPlayerMove/OnZombieSpawn/OnZombieDead/OnItemPickup/OnSound/...` | `src/script/EventBridge.cpp:16-195`、`src/core/GameEvents.h` |
| Host API | v1 薄包装：`Game/Player/World/Zombies/Items/Hud/UI/Menu/Inventory/Save/Content` | `src/script/ScriptApi.h:60-139`、`ScriptApi.cpp:83-765` |
| 单机动态内容 | `Content.RegisterItems/Recipes/Buildings/Pois/Missions` | `ScriptApi.cpp:506-746` |

### 1.2 瓶颈：API 太薄，脚本只能"看见"很少的状态

`ScriptApi` 目前能读的玩家信息只有位置、HP 和背包 UI 快照；以下内容全部只能 C++ 访问：

- 需求：`Needs.hunger/thirst/fatigue`（`src/characters/components/CharacterComponents.h:219-228`）
- 伤口 / 疼痛 / 感染 / 体温：`CombatComponents.h:165-255`、`CharacterComponents.h:232-253`
- 技能 / XP / Perk：`ProgressionComponents.h:34-51`、`ProgressionRules.h:91-158`
- 背包逐条物品 / 装备槽：`items/ItemComponents.h:14-56`
- 附近实体（同伴/动物/载具/容器/地面物品）：只有僵尸有 `Zombies.Count/GetPosition`
- 制作 / 建造 / 任务状态：`CharacterComponents.h:39-48`、`BuildingRules.h:23-39`、`MissionComponents.h:24-28`
- 击杀归属：`OnZombieDead.killer` 曾恒 0；M35-F2-T1 已改为转尸体时读取 `LastDamage.sourceId`。
- 跨存档脚本状态：没有 `Mod.Data`

结果：任何"看状态 → 做判断 → 给反馈"的内容，都只能落到 C++，然后编译。

### 1.3 目标工作流

1. **纯数据**：新物品/配方/作物/建筑/POI/任务/世界事件 → `content/*.json`，不编译。
2. **规则/反应**：波次导演、挑战模式、赏金、环境事件 → Lua mod，读取状态 + 事件 + 动作，不编译。
3. **有状态玩法**：多阶段任务、最佳成绩、解锁进度 → Lua + `Mod.Data`，不编译。
4. **只有新系统**：需要新 ECS 组件/新渲染/新网络协议 → 一次性补 C++，同时把可复用部分暴露成 API。
5. **新增玩法动作**：如果只是现有动作的另一种触发方式，优先走 `Player.* / Craft.* / Build.*` 命令化 API，不新增 C++ 玩法分支。

## 2. 目标与非目标

### 2.1 目标

- 把**读状态、收事件、做动作、存状态**四件事补齐，使单机内容玩法可以纯脚本交付。
- API 从 v1 升到 v2；v1 mod 不改一行继续加载。
- Lua / Python 同一套签名、同一套返回结构、同一套事件名。
- 所有写操作有明确边界：单机或命令化；不在联机客户端静默改权威状态。
- 每个新 API 都有单测、双后端烟测、文档和示例。

### 2.2 非目标（M35 不做）

- 服务器端执行脚本、联机脚本内容同步（留给后续 M36；M35 的写 API 在多人下失败关闭）。
- 脚本注册贴图/图集/音频资源（图集已有 content 管线；音频只播放已有 clip）。
- 任意 ECS 访问、任意组件读写、任意文件/网络访问。
- 自定义 AI / 寻路 / 渲染管线。
- 修改现有 content JSON 格式；新字段只做可选扩展。
- 把现有 C++ 系统改成脚本驱动（只暴露，不搬迁）。

### 2.3 M35 之后仍然需要 C++ 的边界

| 需求类型 | 能否脚本/数据交付 | 说明 |
|---|---|---|
| 新物品/配方/作物/建筑/POI/任务/世界事件 | ✅ JSON | 已有 content 管线 |
| 状态驱动的规则/事件/UI/挑战 | ✅ Lua | F1–F3 后 |
| 有进度的活动/成绩/解锁 | ✅ Lua + Mod.Data | F4 后 |
| 新的武器机制（新伤害类型、复杂弹道、状态效果） | ❌ | 需要 C++ 战斗/物品系统 |
| 新的 AI 行为（巡逻/掩体/编队） | ❌ | 需要 C++ AI/寻路；脚本只能读状态、下命令 |
| 新的原生 HUD 控件/动画 | ⚠️ | 脚本 UI 可做面板；原生 HUD 需要 C++ |
| 新资源类型（新音频/图集之外的资产） | ❌ | 需要资源管线 |
| 联机脚本内容同步 | ❌ | M36 |

> 判断口诀：**"改数值/改触发条件/改流程编排"→脚本；"新增一套底层规则/新组件/新协议"→C++ 一次，然后把可复用部分暴露成 API。**

## 3. API v2 设计原则

### 3.1 版本与兼容

- `ScriptApi::kApiVersion` 从 `1` 升到 `2`（`src/script/ScriptApi.h:62`）。
- `ModLoader` 已实现"`api` 大于当前拒绝、小于当前告警并尽力加载"（`ModLoader.cpp:62-73`），因此：
  - v1 mod（`"api": 1` 或省略）继续加载，日志一条告警；
  - v2 mod 使用新 API；
  - 新 API 不改变任何 v1 函数签名/返回值。
- 新增 `Game.GetApiVersion()`，便于 mod 自己判断。

### 3.2 命名与返回

- 全局表继续用 PascalCase 函数：`Game`、`Player`、`World`、`Entities`、`Craft`、`Build`、`Mission`、`Mod`、`Json`、`Audio`。
- 只读单对象：返回 table 或 nil（Lua `nil` / Python `None`）。
- 只读列表：返回 `{count, items=..., truncated}` 或直接数组；同一 API 内保持一致。
- 写动作：统一返回 `{ok, queued, error}`：
  - `ok`：动作被接受；
  - `queued`：已提交命令、结果稍后由事件/HUD 体现（联机）；
  - `error`：拒绝原因（中文，可直接打日志）。
- 现有 v1 写 API（`Player.Teleport/AddItem`、`World.SpawnItem`、`Zombies.Spawn`、`Content.Register*`）保持原有调用兼容；F3-T6 只给 `Zombies.Spawn` 追加可选 `variant`，旧三参调用不变。

### 3.3 稳定 ID、坐标与 nil

- 实体句柄一律 `uint64 StableId`，`0` = 无效；跨存档稳定（`ecs::StableId`）。
- 坐标为格（浮点 x/y + 楼层 z），与 v1 一致。
- 查询目标不存在返回 nil / 0 / false；写动作返回 `{ok=false,error=...}`，不抛异常。
- 所有列表查询有上限，超过时 `truncated=true`，不静默丢数据。

### 3.4 单机 / 联机边界

脚本系统当前只在客户端初始化（`GameApp.cpp:705-746`）；`allowDynamicContent` 仅在 `net.mode=direct` 为 true（`GameApp.cpp:168-169`）。因此：

| 类别 | 单机 direct | 联机 loopback/client（含主机） |
|---|---|---|
| 只读查询 | 可用 | 可用（读客户端副本） |
| 命令化动作（Use/Equip/Pickup/Attack/Craft/Build） | 立即执行 | 提交命令，服务器权威执行 |
| `Player.GiveXp/ApplyDamage/AdjustNeeds`、`Craft.Learn`、`Build.CanPlace` | 可用 | **拒绝**（`ok=false`） |
| `World.EmitSound` | 可用（本地） | **拒绝**（不跨端派发） |
| `Mod.Data` 写 | 可用 | **拒绝**；`Get=nil`、`Keys` 空 |
| `Content.Register*` | 可用（现状） | 拒绝（现状） |
| 新事件（OnDamage/OnCraft/...） | 可用 | M35 不保证；需要事件时按现有复制事件为准 |

> 设计取向：**先让单机内容产能起飞**，联机脚本留到 M36。M35 的所有新写 API 必须在多人下 fail-closed，不能像 `Player.Teleport` 那样直接改本地副本。v1 兼容例外（`Player.Teleport/AddItem`、`World.SpawnItem`、`Zombies.Spawn`）保持原有本地行为，便于旧 mod 不改代码继续运行；新 API 不沿用该例外。

### 3.5 双后端契约

- 所有新函数在 `ScriptApi` 里只依赖 entt/游戏类型，返回 POD 结构体；Lua/Python 绑定层各自把 POD 转成 table/dict。
- 不在 `ScriptApi` 里创建 Lua/Python 对象，避免两份复杂绑定。
- 新增 API 必须同时改：
  - `src/script/LuaRuntime.cpp` 的 `BindApiTables`；
  - `src/script/PythonRuntime.cpp` 的对应绑定；
  - `docs/modding.md` 3.x / 4.x；
  - `docs/03-脚本系统设计.md` §4.2 / §5 验收表。
- 测试用同一组输入分别驱动 Lua/Python，比较关键字段（数值容差、字符串完全一致）。

### 3.6 错误、日志与性能

- 非法参数：返回失败 + `ZL_WARN("script-api", ...)`，不崩游戏。
- `OnTick` 中高频查询：单次查询上限默认 32、最大 128；半径默认 8、最大 32；超出截断并 `truncated=true`。
- 列表 API 的排序必须确定：按距离升序，再按 StableId 升序。
- 新增查询不改变现有 tick 预算；不做每帧全量 ECS 扫描，优先 `SpatialIndex::ForEachInChunks`（`src/ecs/SpatialIndex.h`）。
- F5-T4：`Entities.Query` 按 mod 归属、按 tick 计数；每 mod 每 tick 汇总一次日志，截断日志每 mod 每 tick 首条，后续仅计数，不做额外硬限流。

## 4. API 规格

> 下表是 M35 的目标契约。标注 `SP` = 单机 direct 可用；`MP` = 联机客户端可用；`Cmd` = 走 `net::Command` 命令层。

### 4.1 `Game`

| API | 返回 | 说明 | SP | MP |
|---|---|---|---|---|
| `Game.GetApiVersion()` | number | 当前 API 版本（2） | ✓ | ✓ |
| `Game.IsMultiplayer()` | bool | 存在 `NetworkClient` 或命令管线非 Direct（主机/加入/loopback 都为 true） | ✓ | ✓ |
| `Game.GetNetMode()` | string | `direct/loopback/client`（主机与加入统一为 `client`；`client` 表示走网络） | ✓ | ✓ |

现有 `GetTick/GetTime/GetPlayerId/ToggleInventory/...` 不变。

### 4.2 `Player` 只读

| API | 返回 | 字段 | 说明 |
|---|---|---|---|
| `Player.GetNeeds()` | table/nil | `hunger,thirst,fatigue,nutrition,health,healthMax,moveScale,damageScale,warning` | 需求值 0~1，0=满足；`nutrition` 来自 `FoodState` |
| `Player.GetStamina()` | table/nil | `current,max,exhausted` | `CombatStamina` |
| `Player.GetWounds()` | table/nil | `{count,wounds=[{type,severity,bandaged,bleeding}]}` | `Wounds`；`type` 为 `blunt/bite/claw/fire/debug` |
| `Player.GetPain()` | table/nil | `level,baseLevel,reliefRemaining` | `Pain` |
| `Player.GetInfection()` | table/nil | `stage,progress,slowRemaining,timeToNextStage` | `stage` 为 `none/incubating/fever/severe` |
| `Player.GetClimate()` | table/nil | `bodyC,wetness,ambientC,effectiveC,insulation,waterproof,indoor,nearFire,warning` | `Climate` |
| `Player.GetProgression()` | table/nil | `{level,xp,xpNext,perkPoints,skills={melee={level,xp,xpNext},...},perks=[...]}` | 需要新增 `GameContext::progressionConfig` 指针 |
| `Player.GetInventory(offset?,limit?)` | table/nil | `{weightKg,capacityKg,totalStacks,stacks=[...],truncated}` | 逐条 `ItemInstance`，见 §5.2 |
| `Player.GetEquipment()` | table/nil | `{primary=stack|nil, body=stack|nil}` | `Equipment` 两个槽 |
| `Player.CountItem(defId)` | number | - | 仅背包，不含装备槽 |
| `Player.HasItem(defId,count?)` | bool | - | 仅背包；`count` 缺省 1 |

注意：

- 背包索引 `index` 为 **0-based**，与 `Inventory.Action` 一致；Lua 里不要拿它直接当数组下标。
- `GetInventory` 不依赖背包 UI 是否打开，直接读 `ecs::Container`。
- 不返回未注册 defId 的完整定义；未知物品仍保留 `defId`、`name=""`、`weightKg=0`（旧档/删 mod 场景）。

### 4.3 `Player` 写动作

| API | 返回 | 说明 | 实现 |
|---|---|---|---|
| `Player.UseItem(index?)` | result | `index` 缺省 -1 = 第一件可用消耗品 | `net::CommandType::UseBag` |
| `Player.EquipItem(index,slot?)` | result | `slot` 为 `"primary"`/`"body"` 或 0/1，缺省 primary | `EquipBag` |
| `Player.Unequip(slot)` | result | 同上 | `Unequip` |
| `Player.DropItem(index)` | result | 丢弃整堆；`-1` = 第一堆 | `DropBag` |
| `Player.PickupNearest()` | result | 拾取最近地面物品 | `PickupNearest` |
| `Player.Pickup(entityId)` | result | 拾取指定地面物品 | `PickupEntity` |
| `Player.Attack(targetId?,heavy?)` | result | `targetId=0` = 自动瞄准最近 | `Attack` |
| `Player.ApplyDamage(amount,damageType?)` | result | 走 `CombatSystem::ApplyDamage`，受护甲/格挡/闪避影响；`damageType` 缺省 `"blunt"`，支持 `blunt/bite/claw/fire/debug` | SP 直调 |
| `Player.AdjustNeeds(hunger?,thirst?,fatigue?)` | result | 增量，钳制 [0,1]；正数 = 更饿/更渴/更累；负值/NaN 拒绝 | SP 直调 |
| `Player.GiveXp(skill,amount)` | result | `skill` 为 `melee/building/crafting/survival`；返回 `characterLevels/skillLevels/perkPoints/characterXp/skillXp`；内部调用 `AwardXp + RefreshDerived` | SP 直调 |

动作语义：

- `Cmd` 类动作统一走 `GameContext::submitPlayerCommand`（由 `WorldDemoState` 提供，内部处理 direct 命令管线 / loopback / KCP），**不要在 ScriptApi 里分网络模式**。
- `Cmd` 类动作单机走 direct 命令管线，**立即执行**；联机走 loopback/KCP，服务器执行，`queued=true`。
- 单机 direct 下 `ok=true` 只代表命令被接受；例如 `UseItem` 指向不可用物品时，物品逻辑仍会拒绝并 HUD 提示。脚本需要结果时监听 `OnItemUsed/OnCraftFinished/OnDamage` 或轮询状态。
- `Player.ApplyDamage` 不绕过护甲/格挡/闪避；脚本想造成"真实伤害"时用 `damageType="debug"`（与现有 F6 调试伤害一致，护甲/格挡不减免）。接口没有方向参数，有 `Facing` 时按"正面来袭"处理，使格挡/弹反仍可参与；`Fire`/`Debug` 不可格挡。`ok=true` 只表示已进入伤害管线，闪避/弹反/完全格挡时实际扣血可能为 0，以 `OnDamage` 或 `Player.GetHealth()` 为准。
- `Player.AdjustNeeds` 不触发食物中毒/营养逻辑，只改数值；食物效果仍应通过 `UseItem`。负增量不是"恢复"接口，统一拒绝；需要降低需求时用食物/睡眠。
- `Player.GiveXp` 的 `ok=true` 返回本次奖励快照；`perkPoints` 是本次新增点，不是玩家当前总点数。`skill` 未知、`amount<=0`/NaN、成长配置缺失或关闭时返回 `ok=false`。

### 4.4 `World` 与 `Entities`

`World` 保持地块/物品生成；新增实体查询放 `Entities`，避免 World 表过长。

#### `World`

| API | 返回 | 说明 | SP | MP |
|---|---|---|---|---|
| `World.SpawnItem(defId,x,y,z?)` | bool | 生成一个地面物品；defId 必须已注册 | ✓ | ✓（本地副本；联机不推荐） |
| `World.GetWeather()` | table | `{kind="clear/rain/fog/cold",ambientC,isNight}` | ✓ | ✓ |
| `World.GetTimeOfDay()` | number | 0~1，来自 `GameTime::DayFraction()` | ✓ | ✓ |
| `World.EmitSound(x,y,radius,kind?,clip?)` | bool | 通过 `SoundManager::EmitWorldSound`，进入 `OnSound`/AI 听觉 | ✓ | —（拒绝） |

`World.EmitSound` 的 `radius` 必须在 `(0,256]`；`kind` 缺省 `generic`，支持 `generic/gunshot/impact/footstep/growl/zombie_growl/zombie/ui/vehicle`。`clip` 为空时由音频系统按 `kind` 选默认音效。仅 Direct 可用；非 direct 返回 `false`，不广播。服务器权威引怪仍由服务器自身的枪声/撞击/载具等路径负责。

现有 `World.IsPassable/GetSquare/SpawnItem` 不变。

#### `Zombies`

| API | 返回 | 说明 |
|---|---|---|
| `Zombies.Spawn(x,y,z?,variant?)` | number | 生成僵尸，返回稳定 ID；`0` = 失败 |
| `Zombies.Count()` | number | 当前实体僵尸数（不含离屏虚拟僵尸） |
| `Zombies.GetPosition(handle)` | table/nil | `{x,y,z}`；死亡/不存在 → nil |

`variant` 缺省 `normal`，支持 `normal/fast/strong/armored`；未知值返回 `0` 并记录警告。四种变体分别使用现有生成配置：HP 100/70/170/200，速度倍率 1.0/1.55/0.78/0.62，视觉效果与减伤/抗击退沿用 `ZombieVariantProfileFor`。`z` 目前仍只支持地面层语义（与原 API 一致）。

#### `Entities`

| API | 返回 | 说明 |
|---|---|---|
| `Entities.Get(id)` | table/nil | 实体摘要，见 §5.3 |
| `Entities.Query(x,y,z,radius,kind?,limit?)` | table | `{count,truncated,entities=[...]}`；按距离排序 |
| `Entities.GetContainer(id)` | table/nil | 容器/仓库/车辆货箱内容，见 §5.3 |

`kind` 支持：

```text
any | player | zombie | animal | companion | npc | vehicle |
container | storage | item | corpse | fire
```

规则：

- 只返回已加载、`Alive` 的实体；虚拟化僵尸（LodState 离屏）不返回。
- `radius` 默认 8、最大 32；`limit` 默认 32、最大 128。
- `Entities.Get` 对不存在的 id 返回 nil；对未识别实体返回 `kind="other"`，仍给位置。
- `Entities.GetContainer` 对未搜索的 `LootContainer` 返回 `searched=false,items=[]`，不提前泄露掉落。
- `storage` 仅 `PlayerStorage`/带 `Container` 的可交互仓库；`vehicle` 货箱在 M35 不做内容枚举（留后续）。

### 4.5 `Craft`

| API | 返回 | 说明 |
|---|---|---|
| `Craft.List()` | table | `{count,recipes=[...],truncated}`；见 §5.4 |
| `Craft.GetState()` | table | `{active,recipeId,outputDefId,outputLabel,outputCount,elapsed,duration,progress,batchTotal,batchCompleted,queue=[{recipeId,count}]}` |
| `Craft.Start(recipeId,count?)` | result | `count` 1~99；映射到 `InventoryActionType::Craft`（`fromIndex=配方索引`） |
| `Craft.Cancel()` | result | 映射到 `CancelCraft` |
| `Craft.IsKnown(recipeId)` | bool | 读 `KnownRecipes` + 非锁定配方 |
| `Craft.Learn(recipeId)` | result | SP；追加到 `KnownRecipes`，未知/已会返回 false |

动作语义：

- `Craft.Start` 先校验 `count=1~99`、配方存在、已学会、制作站（`GameContext::craftStationNearby`）、`items::CanCraft`（材料/工具/锅具/燃料/输出空间），再提交 `InventoryActionType::Craft`（`fromIndex=registry index`）；Direct 立即执行，loopback/KCP 返回 `queued=true`。
- `Craft.Cancel` 只在存在活跃批次或非空队列时提交 `CancelCraft`；无制作时 `ok=false`。Direct/loopback/KCP 路由同 Start。
- `Craft.Learn` 仅 Direct；未知/已会/联机均 `ok=false`，成功直接追加 `KnownRecipes` 并排序去重，不消耗物品。

### 4.6 `Build`

| API | 返回 | 说明 | 实现 |
|---|---|---|---|
| `Build.List()` | table | `{count,items=[...],truncated}`；见 §5.4 | 基础 `LoadBuildableDefs` + `GameContext::modBuildables` |
| `Build.CanPlace(defId,x,y,vertical?)` | result | SP 只读预检；联机 `ok=false` | SP hook（不扣物品） |
| `Build.Place(defId,x,y,vertical?)` | result | 放置可建造物；材料/任务门槛由现有建造逻辑校验 | SP hook / MP `PlaceStructure` |

| `Build.Repair(x,y)` | result | 维修 | SP hook / MP `RepairStructure` |
| `Build.ToggleDoor(x,y)` | result | 开关门 | SP hook / MP `ToggleDoor` |

实现要点：

- 单机 `WorldDemoState` 的建造路径是本地函数（`WorldDemoState.cpp` 建造段），不是命令分支；M35 在 `GameContext` 增加 `buildCanPlace/buildPlace/buildDemolish/buildRepair/buildToggleDoor` 5 个 `std::function` hook，由 `WorldDemoState` 进入赋值/退出清空，ScriptApi 调用 hook。

- 联机仍走既有 `net::Command`（`ServerHost.cpp` 校验 index/坐标/owner/冷却/材料），脚本 API 只负责把 `defId` 映射到 `m_buildables` 索引；`Demolish` 使用 flags=0，由服务器立即执行，不进入 UI 的两次确认。
- `Build.List` 的 `index` 必须与服务器/单机建造目录顺序一致，供 `PlaceStructure` 使用。

### 4.9 `Mod.Data`（跨存档脚本状态）

| API | 返回 | 说明 |
|---|---|---|
| `Mod.Id()` | string | 当前 mod id（便于日志/命名空间） |
| `Mod.Data.Get(key)` | string/nil | 字符串值；不存在返回 nil |
| `Mod.Data.Set(key,value)` | bool | 值必须是字符串，≤4096 字节；非法/超限 false 且不覆盖旧值 |
| `Mod.Data.Remove(key)` | bool | 不存在返回 false |
| `Mod.Data.Keys()` | table/list | 当前 mod 的 key 数组，字典序 |
| `Mod.Data.Clear()` | bool | 清空当前 mod；无数据时幂等返回 true |

约束：

- 最多 256 个 mod；每 mod 最多 64 个 key；mod id ≤ 128 字节；单 key ≤ 64 字节；单值 ≤ 4096 字节；全局 key+value ≤ 128 KB。
- 值为字符串，复杂结构用 `Json.Encode/Decode`；Lua/Python 非字符串值返回 false。
- 持久化到当前存档，随存档保存/加载；**热重载保留**，新游戏/换存档清空。
- 联机失败关闭：`Set/Remove/Clear=false`，`Get=nil`、`Keys` 空；日志每个 mod 每次加载最多警告一次。

### 4.10 `Json`

| API | 返回 | 说明 |
|---|---|---|
| `Json.Encode(value)` | string/nil | table/array/string/number/bool → JSON 文本；失败 nil/None |
| `Json.Decode(text)` | value/nil | JSON 文本 → Lua table / Python dict/list；失败 nil/None |
| `Json.Array()` | array | 空数组标记；`Json.Encode(Json.Array()) == "[]"` |
| `Json.Null()` | null | null 标记；Lua 解码 JSON null 得到该标记，Python 得到 `None` |

限制：容器深度 ≤ 16、单个字符串 ≤ 64 KB、数组/对象 ≤ 1024 项；数字必须有限；循环引用直接失败并 `ZL_WARN`。Lua 空 table 编码为 `{}`（对象），连续整数 key `1..N` 的 table 编码为数组；对象 key 必须是字符串，数字/混合 key 非数组时失败。Lua 顶层 `nil` 按 null 编码；嵌套 null 用 `Json.Null()` 保留。Python 用 `dict`/`list`，dict key 必须是 `str`。编码对象 key 排序，保证双后端输出稳定。

> Lua 没有内置 JSON；`Json` 是 M35 对 Lua 的主要生产力补充。Python 后端包装标准 `json`，由 C++ 预校验类型/深度/大小/循环后调用 `json.dumps/loads`，保持同名与相同限制。

### 4.11 `Audio`（F5-T3 已交付）

| API | 返回 | 说明 |
|---|---|---|
| `Audio.Play2D(clip,volume?)` | bool | 播放 `assets/audio/<clip>.wav` 或现有 clip 名 |
| `Audio.Play3D(clip,x,y,radius?,volume?)` | bool | 世界空间播放；不进入 AI 听觉（要引怪用 `World.EmitSound`） |

说明：只播放已有 clip，不注册新资源；`clip` 仅字母/数字/`_`/`-`，不含路径/扩展名；`volume` 有限并钳制 0~1，`radius` 0~256；设备关闭/引擎未就绪/文件缺失 no-op + false。`Play3D` 不写 `OnSound`，不进入 AI 听觉。

### 4.12 Lua 多文件 `require`（F4-T4）

```lua
-- scripts/main.lua
local util = require("util")          -- scripts/util.lua
local wave = require("wave.director") -- scripts/wave/director.lua
```

规则：

- 只允许 `<modRoot>/scripts/**` 下的 `.lua`；禁止 `..`、绝对路径、symlink 逃逸。
- 先按 `require` 参数相对 `scripts/` 解析；以 `./` 开头时相对当前文件目录。
- 每个 mod 独立缓存；返回模块 `return` 值，未返回则 `true`。
- 热重载清空缓存；单文件 ≤ 1 MB；递归深度 ≤ 32。
- Python 后端 M35 不提供本地模块 import（仍单文件），文档明确。

实现（2026-11-20）：`require` 是每个 mod 环境内的 C 闭包，缓存/加载中表作为 Lua upvalue 随环境 GC，`ReloadMod` 新建环境即清空。模块名支持 `util`、`wave.director`（点号转目录）、可选 `.lua` 后缀；`./`/`.\` 从调用文件所在目录解析（嵌套模块同样适用）。路径先规范化并拒绝空段、`.`/`..`、绝对路径、盘符/冒号，再用 `weakly_canonical` 解析 symlink，要求最终文件仍在 canonical `<scripts>/` 前缀内；只接受普通 `.lua` 文件，读取前后都检查 1 MB。循环用 per-mod 加载中集合检测；深度按嵌套 require 计数，超过 32 层报错。模块在同一个 mod 环境执行，缓存按 canonical 路径，返回 `return` 首值（无返回值/`nil` 归一为 `true`）；解析/加载/执行错误都带调用文件行号，模块运行时错误还带模块路径、行号与 traceback。Python 仍单文件，`import` 仅白名单标准库，不支持本地模块。

## 7. 持久化：`Mod.Data`

### 7.1 方案选择

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 独立 `mods_data.json` 文件 | 与 ECS 解耦 | 需要改 SaveService/SaveRequest/管理后台写盘；联机/服务器要单独同步 | 不采用 |
| 玩家实体组件 | 复用现有存档 | 玩家死亡/重开可能换实体；只能存"玩家"数据 | 不采用 |
| 世界单例实体 + 组件 | 复用 `CaptureEntities`（所有带 StableId 实体都会存，无 Position 自动进 global 桶）、加载零改动 | 需要新增一个组件 codec | **采用** |

依据：`EntityStore.cpp:156-191` 对所有带 `ecs::StableId` 的实体做快照；`RegionEntityBuckets.cpp:87-93` 对无 `Position` 的实体放入 global 桶；`ComponentRegistry` 提供通用注册接口（`ComponentRegistry.h:138-208`）。

### 7.2 组件与编码

```cpp
// 新增：src/script/ModDataComponents.h
namespace zl::ecs {
struct ModDataTag {};  // 单例实体标记

struct ModDataEntry {
    std::string key;
    std::string value;
};

struct ModData {
    // modId → 有序 key/value；用 vector 保证二进制编码确定
    std::vector<std::pair<std::string, std::vector<ModDataEntry>>> mods;
};
}
```

- 新 magic：`MakeMagic('M','D','A','T')`（`ComponentRegistry.h` 当前未占用）。
- 版本 v1；旧存档无该组件 = 空数据。
- 编码：u32 mod 数 → 每个 mod：string id + u32 entry 数 → 每个 entry：string key + string value；读取时校验上限。mod 数 ≤256、mod id ≤128 bytes、每 mod 64 个 key、key ≤64 bytes、value ≤4096 bytes、全局 key+value ≤128 KB；重复 mod id/key、控制字符、超限均拒绝。
- 注册到 `RegisterBuiltinComponents`，与 `Progression/MissionLog` 同级。`ModDataTag` 本身不单独注册 codec；读档时 `MDAT` codec 在还原 `ModData` 后补挂 tag，保证加载后的单例仍可被找到。
- 单例实体惰性创建：第一次 `Mod.Data.Set` 时 `ecs->Create()` + `ModDataTag` + `ModData`；读取/写前查找优先 `view<ModData>`（兼容加载后尚未补 tag 的实体），没有就返回空；`EnsureModData` 只创建一个。
- 不挂 `Position/SpriteRef`，不参与渲染/物理/复制；只进存档 global 桶。

### 7.3 生命周期

| 时机 | 行为 |
|---|---|
| 应用启动/脚本加载 | 不创建实体；`Mod.Data.Get` 返回 nil |
| `OnWorldStart` | 存档已加载，组件可读；脚本可恢复状态 |
| 游戏中 `Set` | 立即写入组件；下一次存档快照包含 |
| 热重载脚本 | 组件保留；新脚本可继续读 |
| 快速存档/自动存档 | 随实体快照写入 |
| 读档 | 组件由 codec 还原；旧档无数据 = 空 |
| 新游戏 | 新世界无实体 = 空 |
| `OnWorldExit` | 同步调用，可做清理；自动存档随后捕获 |

需要注意：`OnSaveBegin` 在快照提交之后才发出（`WorldDemoState.cpp:1748-1777`），**不能**在 `OnSaveBegin` 里补写本次存档；需要在正常游戏过程中写，或写完后调用 `Save.QuickSave()`。

### 7.4 限制与失败语义

- `Set` 先复制并校验再提交；超 mod/key 数、单值/全局字节上限、非法 mod id/key、非字符串值均返回 false，不覆盖旧值、不产生部分写入。
- `Remove` 不存在返回 false；移除最后一个 key 时同时移除该 mod 条目；`Clear` 无数据/无该 mod 时幂等返回 true。
- `Keys` 按字典序返回；联机下为空表。
- 联机：`allowDynamicContent=false`（非 direct）时 `Set/Remove/Clear` 返回 false，`Get` 返回 nil，`Keys` 为空；每个 mod 每次加载最多警告一次，避免刷屏。
- `Mod.Data` 不参与内容指纹；换 mod 不会自动清理旧数据；重新安装同名 mod 可恢复。

## 10. 每阶段能解锁的内容玩法

| 阶段 | 可以纯脚本做的玩法 |
|---|---|
| F1 完成后 | 自定义 HUD/仪表盘、条件提示、动态难度、根据状态触发的旁白/事件、附近实体搜索与标记、任务追踪面板 |
| F2 完成后 | 击杀赏金/连杀、伤害统计、受击反馈事件、制作/建造成就、搜刮图鉴、死亡归因/战报 |
| F3 完成后 | 脚本引导的自动使用/装备/拾取、脚本化制作、基地自动建造、NPC/同伴交互、战斗教学、挑战模式动作限制 |
| F4 完成后 | 多阶段活动、最佳成绩、解锁进度、随机种子/状态持久化、大型多文件 mod、JSON 配置驱动 |
| F5 完成后 | 完整"脚本内容包"交付：尸潮导演、生存挑战、动态 POI 事件、脚本 UI 面板、示例模板 |

### 典型玩法配方

1. **尸潮导演**：`OnTick` 按天数/`World.GetTimeOfDay` 刷 `Zombies.Spawn(variant)`；`OnDamage/OnZombieDead` 计分；`Mod.Data` 存最高波次。
2. **限时撤离**：`Game.SetTimer` + HUD 倒计时；`Entities.Query` 找撤离点附近实体；超时 `Player.ApplyDamage`。
3. **赏金猎人**：`OnZombieDead.killer` 归属；`Player.GetInventory` 校验目标物品；`Player.GiveXp` + `Hud.SetField`。
4. **搜刮图鉴**：`OnLootSearched` + `Items.GetInfo` 记录表；`Json` 存图鉴；完成度显示在脚本 UI。
5. **环境恐怖事件**：`OnSound` 触发 `World.EmitSound`/`Audio.Play3D`；`Entities.Query` 检查玩家周围；刷怪+旁白。
6. **生存挑战规则**：读 `Player.GetNeeds/GetInfection`；禁止/强制 `Craft.Start`；`Mod.Data` 存规则与成绩。
7. **同伴小队**：`Entities.Query(kind="companion")` + `Entities.Get`；HUD 显示同伴状态；`Companion` 命令 API 留后续。
8. **动态 POI 事件**：`Entities.Query(kind="container")` + `World.GetContainer`；按搜刮进度触发 `OnLootSearched` 奖励。
9. **建造限制/自动化**：`Build.List/Place` + `OnBuildPlaced`；例如"每晚自动补墙"或"只允许木墙"挑战。
10. **脚本 UI 仪表盘**：`Player.GetStatus` + `Game.GetTime` + `World.GetWeather`，用 RML 画面板；不依赖 native HUD 改动。

### 11.4 性能

- 脚本关闭 vs 开启：同一场景 60 秒平均帧时间差 ≤ 5%（Debug 参考）。

### 11.5 手工验收

## 13. 风险与已定决策

| 风险 | 影响 | 缓解 |
|---|---|---|
| API 面膨胀 | 维护成本/双后端漂移 | POD + 绑定层直译；每个 API 双后端测试；文档表 |
| 单机/联机语义不一致 | 脚本在多人下静默失效 | 新写 API 全 fail-closed；`Game.IsMultiplayer()`；文档明确 |
| SP/服务器逻辑重复 | 事件/动作两套实现漂移 | M35 先单机；共用低层函数；M36 统一服务器脚本 |
| `OnGameStart` 语义历史错误 | mod 初始化时机错 | 新增 `OnWorldStart/Exit`；文档纠正；示例迁移 |
| `ModData` 存档膨胀 | 存档变大/读写慢 | 256 mod/64 key/4KB/128KB 上限；写入即校验 |
| 脚本查询太重 | 帧率下降 | 半径/数量上限；SpatialIndex；性能用例 |
| Lua/Python JSON 差异 | 双后端结果不同 | 固定深度/数组/空表规则；对照测试 |
| `require` 路径逃逸 | 本地文件泄露（信任本地 mod，但仍防手滑） | canonical path + 前缀校验；禁止 `..`/绝对路径 |
| 旧档/旧 mod 回归 | 老内容崩溃 | v1 签名不变；旧档无组件=空；全量回归 |

### 已定决策（实施时按此执行）

1. `OnDamage` 只发 `applied && amount>0`；完全格挡/闪避不发，另给 `blocked` 字段区分普通格挡剩余伤害。
2. `OnCraftFinished` 失败/中断也发，`failed=true`，便于脚本恢复 UI；无效的 `Craft.Start` 不发开始事件。
3. `Build.Place` 已随 F3-T5 提供 `Build.CanPlace(defId,x,y,vertical?)` 只读预检，避免脚本盲试。
4. `Mod.Data` M35 只做存档内；跨存档留后续 `Mod.GlobalData`。
5. Python 本地模块 import M35 不做；Lua `require` 优先，Python 用户继续单文件。
6. 不把 `OnZombieDead` 重命名为 `OnEntityDead`；新增 `OnAnimalKilled`，避免破坏 v1。
