# M31 无缝大地图设计与实施计划（规划稿）

> 状态：**M31-T10 已完成（2026-11-10），等待用户实机验收；T0–T10 已完成：T0 基线、T1 数据契约、T2 36×36 地图、T3 流式/区域 LOD、T4 world manifest/区域桶、T5 道路图/地形/密度、T6 区域事件/冻结/存档/HUD、T7 世界地图/发现/路标/长距离导航、T8 联机多区域兴趣/AOI/服务器 manifest、T9 性能/存档体积/长时稳定性、T10 垂直切片/单机+双客户端验收**。
> 目标：把当前“单张小地图 + chunk 流式加载”升级为**有限边界的大区域无缝世界**，并保证存档、联机、性能和内容密度可控。
> 执行方式：先由用户确认本文件的范围与默认决策，再按 `M31-T0 → T10` 逐个任务实施；每个 T 完成后停下汇报，禁止跳 T。

## 1. 结论先行

### 1.1 可以做，但先做“有限无缝”，不做“无限程序化”

当前工程已经具备：

- `Cell 300×300 格` / `Chunk 10×10 格` 的四级坐标；
- `ChunkManager` 的相机中心流式加载/卸载、后台解析、主线程挂接预算；
- 稀疏地图（缺失 chunk = 默认地形）和每 chunk 的修改 diff；
- `ChunkDiff`、删除墓碑、服务器世界存档、玩家档案和旧版本回退；
- 已加载 chunk 的物理静态体、寻路缓存、动物/火焰等生命周期回调；
- 多 POI、聚落、载具、任务、联机 AOI 复制基础。

所以**跨 chunk 移动已经是无缝的**；真正的新增工作是：

1. 大范围世界内容生产；
2. 未加载区域的状态持久化；
3. 区域级导航/生成/LOD；
4. 多玩家分散区域时的服务器加载与存档；
5. 世界地图、快速移动和内容密度设计。

**建议第一版只做有限边界**：目标 `36×36 chunks = 360×360 格`，约当前 `village_demo`（12×12 chunks）的 **9 倍面积**。无限世界留到这张有限世界被验证好玩之后。

### 1.2 推荐的第一版形态

- 1 个主聚落/村庄核心；
- 2 个道路节点 POI（加油站、检查站或农场仓）；
- 1 个资源/农业区；
- 1 个工业或军事区；
- 1 条主路 + 1 条支路 + 1 条河流/桥；
- 森林、田地、废墟作为程序化填充；
- 玩家可用载具在区域间移动，地图上能看到道路、POI 和已发现区域；
- 不做无限地图、不扩展 z 轴多层、不做分布式服务器。

## 3. 目标与非目标

### 3.1 目标

- **无缝移动**：在已生成的世界内部跨 chunk/cell 不出现加载画面、传送或卡顿尖峰。
- **有限边界**：世界有明确外边界（森林/河流/山体/封锁道路），边界外不生成内容。
- **可持久化**：玩家在 A 区拆墙、丢物品、停车、尸体、聚落状态，走到 B 区再回来仍一致。
- **可联机**：2–4 个玩家分散在不同区域时，服务器只加载必要区域；每人看到的 chunk/实体一致。
- **可导航**：道路、桥梁、车辆通行性、区域 POI 和世界地图可读。
- **有内容密度**：大区域不是大地图空旷跑路；POI、道路、事件、资源和危险按区域配置。
- **可测试/可回退**：旧地图和旧存档不被破坏；大世界出问题可关闭 `world.m31.enabled` 回到当前地图。

### 3.2 非目标（第一版明确不做）

- 不做真正无限程序化世界；
- 不做 3D/多层 z 轴、地下城、跨层寻路；
- 不做分布式服务器/跨进程区域服；
- 不做完整随机剧情生成器；
- 不新增正式美术/音效资源，使用现有占位资源；
- 不在第一版做无缝昼夜区域天气差异（天气仍全局/按配置）；
- 不重写地图 JSON 为二进制，等性能测试证明需要再做 v2。

## 4. 总体设计

### 4.1 数据分层

保持现有格式，新增 **sidecar 世界描述**，避免破坏 `zomboidlike-map-v1` 加载器：

```
assets/maps/<mapName>/
├─ map.json                    # 保持 zomboidlike-map-v1：bounds/legend/defaultFloor
├─ world.json                  # 新增 zomboidlike-world-v1：区域图/道路/POI/生成器元数据
├─ chunks/...                  # 保持现有 chunk_<cx>_<cy>.json
└─ templates/                  # 可选：作者制作的 POI stamp（局部坐标）

config/game.json               # 运行时开关、加载半径、密度、性能预算
saves/<saveId>/
├─ save.bin                    # 现有玩家/世界头
├─ world/
│  ├─ chunk_x_y.bin             # 现有 chunk diff；只保存脏 chunk
│  └─ world_manifest_v1.bin     # 新增：mapHash/seed/generatorVersion/区域状态
└─ entities/                    # 规划：按区域/兴趣分桶的实体快照（或保留现有 EntityStore 并加索引）
```

**关键约束**：

- `map.json` 仍是唯一 chunk 加载入口；`world.json` 不参与 chunk 坐标解析。
- `world.json` 是区域/道路/POI/生成信息的**唯一内容源**；生成器负责产生它，不手改 `config/game.json` 的坐标副本。
- T10 例外：运行时 POI 容器/守军/任务放在地图目录外的 `village_demo_m31_content.json`，由内容指纹覆盖；它不参与 `mapHash`，避免地形身份与运行时内容耦合。
- 旧存档没有 `world.json`/manifest 时按当前地图旧路径加载；新功能只在新存档或成功迁移后启用；默认 M31 下旧 `village_demo` 档需显式 `world.m31.enabled=false`。

### 4.2 `world.json` 契约（草案）

```json
{
  "format": "zomboidlike-world-v1",
  "mapId": "village_demo_m31",
  "seed": 20261109,
  "generatorVersion": 1,
  "bounds": { "chunkX0": 0, "chunkY0": 0, "chunksX": 36, "chunksY": 36 },
  "regions": [
    {
      "id": "village_core",
      "rect": { "chunkX": 2, "chunkY": 2, "chunksW": 8, "chunksH": 8 },
      "biome": "village",
      "poiIds": ["village_haven", "clinic"]
    }
  ],
  "nodes": [
    { "id": "village_haven", "kind": "settlement", "x": 24.5, "y": 26.5 },
    { "id": "road_junction", "kind": "junction", "x": 120.0, "y": 120.0 }
  ],
  "edges": [
    { "a": "village_haven", "b": "road_junction", "kind": "road", "width": 3.0 }
  ],
  "pois": [
    {
      "id": "clinic",
      "template": "clinic_v1",
      "x": 92.0,
      "y": 78.0,
      "radius": 12.0,
      "threat": 2,
      "lootProfile": "poi_clinic"
    }
  ],
  "spawn": {
    "defaultZombieDensity": 0.012,
    "biomes": { "forest": 0.008, "village": 0.020 }
  }
}
```

契约要求：

1. `regions` 的矩形不能重叠；区域必须完整落在 `bounds` 内。
2. `nodes/edges` 构成连通图（除非显式声明 `isolated`）；道路宽度和车辆通行类型进入导航。
3. `pois` 的 `template` 必须存在，模板锚点和半径不越界；POI 的运行时容器/守军/任务仍由现有内容系统扩展。
4. `mapId + generatorVersion + seed` 一起决定基础地形；存档 manifest 必须记录，不匹配时明确报错或只读。
5. 未知字段忽略 + warn；格式版本不认识直接报错，不猜测。

### 4.3 内容生产：作者骨架 + 程序化填充

**原则：程序化只负责“大面积、低信息密度”地形；关键地标必须作者制作/模板化。**

1. **手写/模板 POI**（约 60% 体验价值）：
   - 村庄、医院、检查站、加油站、农场仓、工业区；
   - 每个 POI 用 `templates/poi_*.json` 局部坐标描述，可复用旋转/镜像只在生成器离线烘焙；
   - 室内房间、容器、任务点、守军点、车辆/发电机接入现有数据。
2. **程序化填充**（约 40%）：
   - 森林、田地、草地、废墟、路障、河流/桥；
   - 由 `seed + generatorVersion` 确定性生成；
   - 只生成“可读的地形与少量资源”，不随机生成独特剧情。
3. **内容预算**（第一版）：
   - 1 个主聚落、2–3 个道路 POI、1 个农场、1 个工业/军事区；
   - 主路 1 条、支路 2 条、河流/桥 1 组；
   - 目标 8–12 个可识别地标；任意两个主 POI 距离不小于约 80 格，避免跑路空窗；
   - 每个区域至少有 1 个可见地标/路标/天际线提示。

**产出流程**：

```
作者/模板 → tools/gen_map.py / 新 tools/gen_world.py
  → 生成 chunks/*.json + world.json
  → 校验（bounds/区域重叠/道路连通/POI 模板/密度）
  → 运行时只读加载
```

生成器必须支持 **`--seed` 确定性重跑**；同一 seed + generatorVersion 逐字节一致（或明确记录非确定性例外）。

### 4.4 流式加载与“无缝”边界

复用 `ChunkManager`，不重写 chunk 状态机。新增：

- **世界边界**：相机/玩家在世界外边界内夹取；外层用森林/河流/封锁道路阻断，不出现“虚空墙”；
- **区域预测加载**：按玩家速度/朝向提前加载前方 1–2 个 chunk，保持现有 `requestBudget/attachBudget`；
- **双层半径**：
  - `loadRadius`：完整 loaded（物理/寻路/渲染）；
  - `residentRadius`：仅保留轻量摘要/实体索引（不物理建体，不寻路）；
- **区域冻结**：区域无玩家且超出 resident 后，卸载 chunk，但先保存区域动态状态；
- **禁止**在卸载回调中做长 IO；沿用现有“后台保存/主线程快照”的原则；
- **不改变 chunk 坐标/负坐标约定**；所有分解继续走 `WorldCoords`。

“无缝”的验收不是“无限跑”，而是：

- 连续跨越 10+ 个 chunk 无加载界面；
- 1% 帧时间没有明显长卡顿（阈值见 §8）；
- 卸载后回到原区域，墙/物品/尸体/车辆仍一致。

### 4.5 导航、生成密度与区域 LOD

1. **道路图**：`world.json` 的 `nodes/edges` 生成 `RoadGraph`；长距离寻路先走道路图，再在目标附近接局部 A*。
2. **车辆通行**：为 chunk 增加/派生 `terrainFlag`（road/dirt/forest/water/blocked）；载具只在可通行格移动；桥/浅滩明确通行。第一版不新增复杂车辆 AI，只保证玩家驾驶可读。
3. **区域 LOD**：
   - Active：玩家附近，完整 AI/物理/感知；
   - Ambient：预加载/轻模拟，保留实体摘要；
   - Frozen：仅存档状态，不推进 AI/火焰/动物；
4. **生成密度**：
   - 按 biome/region 配置僵尸、动物、容器、资源节点；
   - 用 `SpawnLodSystem`/虚拟尸群承载远端，不把全图实体实例化；
   - 远处只在区域摘要里记录“尸群/事件”，回到 active 时实体化。
5. **区域事件**：复用 M21 的事件导演；只对 active 区域推进，区域卸载时冻结事件状态，不后台刷怪。

### 4.6 存档与恢复

#### 现有机制

- chunk 修改 = `ChunkDiff`，卸载时写 `world/chunk_x_y.bin`；
- 服务器世界存档保存已加载 chunk diff + 实体；
- 删除用墓碑防复活；玩家/组件有独立版本与旧档回退。

#### M31 新增

1. **世界 manifest**：`world_manifest_v1.bin`，至少记录：
   - `mapId`、`mapHash`、`seed`、`generatorVersion`；
   - 已生成/已修改 chunk 列表、区域解锁/发现状态；
   - 区域级事件/聚落/载具/动物的归属或索引；
   - `worldSaveVersion`。
2. **仍按 chunk 保存 diff**：不要把所有 chunk 合并成巨大 JSON；只保存脏 chunk。大世界文件多时，再按 cell 打包（T9 评估）。
3. **区域实体桶**：车辆、尸体、动物、聚落 NPC、地面物品等按区域/兴趣分桶，避免一个 `entities.bin` 随世界无限增长；保持 StableId 和现有组件版本。
4. **卸载流程**：
   - 主线程冻结区域 → 快照脏 chunk/dynamic entity → 后台写 manifest 分片 → 卸载；
   - 失败保留 dirty 标记，下次重试；
   - 禁止在 chunk 卸载回调中同步写大文件。
5. **读档流程**：
   - 加载 `map.json` + 地图母文件 → 应用 manifest/chunk diff → 恢复区域实体 → 生成玩家 → 流式加载周边；
   - 若 `mapHash` 不匹配：**明确报错并停止**，不静默把旧墙/旧容器套到新地形。
6. **旧档兼容**：
   - 旧存档（无 world manifest）= 按当前单地图路径读取；
   - 新地图/新 manifest 必须走新版本；
   - 不允许“自动把旧档迁移到新生成地形”造成内容错位。

### 4.7 联机（服务器权威、多区域兴趣）

1. **兴趣集合**：每个玩家按自己的位置产生 chunk 窗口；服务器加载所有活跃玩家窗口的**并集**，再按预算排序（靠近玩家、移动方向优先）。
2. **区域独立事件**：事件/守夜/聚落事件归属区域；只有该区域至少有一个在线玩家时推进。
3. **复制**：
   - 继续用现有 `ZLR1`/`ZLCD`/`PlayerState`；
   - 客户端只接收自己 AOI 内的 chunk/实体；
   - 服务器不为无玩家区域生成全量实体，只保留 manifest/dirty 状态。
4. **并发**：
   - 同一 chunk 的建造/拆除/掉落仍走服务器命令串行化；
   - 多玩家在相邻区域时，跨 chunk 的建筑/道路修改必须原子落盘；
   - 聊天/队伍/聚落状态可跨区域，但实体同步仍按 AOI。
5. **第一版目标**：2 个玩家正常，4 个玩家作为 T8 验收压力；超出区域预算时降级加载半径并提示，不崩溃。
6. **协议兼容**：不改变 `SessionProtocol v2`/命令包 v1；如果新增区域订阅/事件包，另立版本与旧客户端拒绝路径。

### 4.8 世界地图、快速移动与内容密度

- **世界地图 UI**：从 `world.json` 生成，不扫描运行时 chunk；显示玩家、道路、河流、聚落、已发现 POI、危险区。
- **发现机制**：靠近/进入 POI 或获得地图物品后标记；未发现区域只显示道路轮廓/迷雾。
- **快速移动**：
  - 第一版**不做任意传送**；
  - 优先通过载具、道路、路标和地图导航解决长距离；
  - 可在后续加“已发现安全屋/聚落”之间的受限快速旅行，必须有燃料/时间/风险成本。
- **密度控制**：
  - 主 POI 间距约 80–120 格；
  - 道路两侧至少每 40–60 格有一个小地标/资源点；
  - 每个区域有明确 biome 和视觉主题；
  - 生成器校验“空区域面积/无地标距离”，不通过则失败或补点。

### M31-T0 基线测量与可行性 Spike

**目标**：在不改变正式存档/协议的前提下，测量当前 chunk 加载、存档、服务器内存和地图文件规模。

- [x] 生成一张临时 36×36 测试地图（仅测量，不接入正式内容）；
- [x] 测量单 chunk 解析/挂接 P50/P95、连续跨越 20 chunk 的帧时间；
- [x] 测量 1 玩家、2 玩家分散时的 loaded chunk 数、内存、CPU；
- [x] 测量当前存档每 chunk diff 大小、1000 个脏 chunk 的写盘时间/文件数；
- [x] 记录基线到 `docs/perf-baseline.md`，给出 M31 预算初值。

**T0 结果（2026-11-09）**：

- **保留 36×36 chunks**，不降级到 24×24/30×30；
- 临时地图 662/1296 个非默认 chunk，443,293 bytes；冷解析 P95 8.33ms、热解析 P95 0.30ms；
- 初始 49 chunk 加载 140.99ms（CPU 62.5ms）；跨 20 chunk 主线程 chunk 工作 P95 0.033ms、max 1.09ms，0 cancelled；
- 2 玩家近似 98 chunks、private 15.27MB、双路 chunk 工作 P95 0.049ms；

## 8. 风险与回退

| 风险 | 影响 | 处理 |
|---|---|---|
| 大地图空洞、跑路无聊 | 体验失败 | POI 模板 + 密度校验 + 道路/地标；T10 已完成，后续仍先验证密度再扩大尺寸 |
| 生成器/地图版本变化导致旧档错位 | 存档损坏 | mapHash + generatorVersion；不匹配明确报错；map 固定版本 |
| 卸载时同步 IO 卡顿 | 帧尖峰 | 主线程快照、后台写、dirty 重试；预算测试 |
| 多玩家兴趣并集太大 | 服务器内存/CPU 爆 | 预算排序、resident 摘要、4 人降级；不追求全图常驻 |
| 区域事件后台乱跑 | 状态不可解释 | 无玩家区域冻结；只推进 active/相邻区域 |
| 寻路跨区失败/绕路 | 载具/任务不可用 | RoadGraph + 局部 A*；桥/水/断头路测试 |
| 文件数/存档体积膨胀 | 读档慢/磁盘压力 | 只存脏 chunk；cell 打包作为 T9 备选 |
| 与现有 M30/联机耦合回归 | 旧功能坏 | 每个 T 全量回归；先开关隔离；旧档回退 |

## 9. 需要确认的默认决策（T0 后）

T0 已按以下默认值完成；T1 开始前如有修改，先改本文件和验收标准：

1. **世界形态**：**T0 数据支持保留有限 36×36 chunks**；不先做 24×24。
2. **是否接受“不做无限世界”**：默认接受，无限留后续。
3. **作者/程序化比例**：默认关键 POI 作者模板、外围程序化。
4. **快速旅行**：默认第一版只用载具/道路，不做任意传送。
5. **旧档**：默认必须兼容；新地图与旧档不自动迁移。
6. **联机规模**：默认 2 玩家完整验收、4 玩家压力/降级。
7. **正式美术/音效**：默认继续占位资源，不阻塞大地图。

如果以上任一项要改，先改本文件和验收标准，再进入 T1。

## 10. 执行协议

- 每个 T 开始前：读本文件对应章节 + 当前代码基线 + 相关 docs；确认依赖已满足。
- 每个 T 结束：只汇报“改了什么、测试结果、限制、下一步”，停下等用户。

- 每个 T 至少：
  - 纯逻辑/数据测试；
  - 至少一条真实 1280/无窗口 smoke（适用时）；
  - Debug + Release 构建；
  - 文档/任务勾选/测试计数更新；
  - `git diff --check`、UTF-8 检查。
- 除非用户明确要求，不提交 Git。
- 先做 T0，T0 数据不达标则先缩小世界尺寸，而不是硬上 36×36。

## 11. 与当前系统的关系

沿用而不重写：

- `WorldCoords` / `Cell` / `Chunk` / `GridSquare`；
- `ChunkManager` 的后台解析、结果队列、attach 预算；

- `PlayerState v20`、`ZLR1`、`ZLCD` 现有复制；
- M21 守夜/事件、M23 聚落/动物/火焰、M25/M26 载具；
- M30 本地战斗表现与 T9 远端姿态。

新增只做“大世界层”，避免把这些系统改造成无法回归的新架构。

## 12. 与 M32 战略层的关系

- M31 提供区域图、道路、世界地图、区域持久化和多区域兴趣；
- M32 在此之上增加区域归属/威胁预警/围攻/失守/夺回/战略资源，规划见 [docs/17-M32区域战略与人类战线.md](17-M32区域战略与人类战线.md)；M32 维持单主角，其他 NPC 只自主支援，不做 RTS 编队/多单位操控；

- 不建议在 M31 垂直切片（T10）前先铺 M32 全图内容。
